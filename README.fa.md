# RigCraft

یک ابزار بررسی سازگاری قطعات کامپیوتر گیمینگ و برنامه‌ریز ساخت سیستم، ساخته‌شده با Django. کاربر رزولوشن هدف را انتخاب می‌کند و بعد قطعات را گام‌به‌گام و به این ترتیب برمی‌گزیند: `GPU → CPU → Motherboard → Cooler → RAM → Storage → PSU → Case`. گزینه‌های ناسازگار هم‌زمان با پیشرفت کاربر خاکستری می‌شوند و سیستم نهایی یک ارزیابی bottleneck و تخمین FPS برای هر بازی دریافت می‌کند.

ساخته‌شده به‌عنوان پروژه‌ی پایانی من برای CS50W.

## تمایز و پیچیدگی (Distinctiveness and Complexity)

این پروژه نه یک سایت فروشگاهی است و نه یک شبکه‌ی اجتماعی یا انجمن، و شباهت نزدیکی به هیچ پروژه‌ی دیگر دوره ندارد (فهرست کارها، وبلاگ یا برنامه‌ی پیام‌رسان نیست). شاید در نگاه اول شبیه فروشگاه به نظر برسد -- بالاخره کاربر قطعات سخت‌افزاری انتخاب می‌کند -- اما هیچ سبد خرید، پرداخت، قیمت‌گذاری یا فرایند خریدی در برنامه وجود ندارد؛ هر صفحه به این پرسش پاسخ می‌دهد که «آیا این قطعات با هم کار می‌کنند؟»، نه «این چقدر قیمت دارد؟» یا «چطور بخرمش؟». این یک مرز طراحی آگاهانه است، نه یک غفلت (بخش «عمداً خارج از دامنه» را در ادامه ببینید).

**یک موتور واقعی بررسی سازگاری با چند قاعده، نه یک فرم ساده.** نُه قاعده‌ی سازگاری مستقل (تطابق سوکت، بررسی پشتیبانی دوگانه از DDR، تناسب TDP و سوکت کولر، فاصله‌ی فیزیکی GPU و رادیاتور، حاشیه‌ی توان PSU) کاملاً سمت سرور و روی انتخاب‌های دسته‌بندی‌شده اجرا می‌شوند و تخطی‌ها را به‌صورت ساختاریافته با `{reason_code, message}` برمی‌گردانند. یک موتور bottleneck جداگانه، که صرفاً اطلاعاتی است، نتایجی را که با تست تجربی کل کاتالوگ مشاهده شده‌اند جست‌وجو می‌کند، به‌جای اینکه یک فرمول زنده محاسبه کند (دلیلش در بخش «تصمیم‌های طراحی» آمده است). قاعده‌های سازگاری روی داده‌ی واقعی قطعات اجرا می‌شوند که در PostgreSQL بارگذاری شده و از منابع نام‌برده‌شده جمع‌آوری شده است (بخش «منابع داده» را ببینید) -- نه داده‌ی ساختگی یا تصادفی. جدول bottleneck حاصل تست‌های دستی خودم است.

**ویزارد ۹ مرحله‌ای با اعتبارسنجی مجدد زنده و دوطرفه، که کاملاً با JavaScript خالص (vanilla) نوشته شده است.** با انتخاب هر قطعه، ویزارد سازگاری هر گزینه‌ی انتخاب‌نشده‌ی مرحله‌ی فعلی را دوباره بررسی می‌کند: endpoint سرور یعنی `/builder/check/` را برای هر گزینه یک‌بار و به‌صورت موازی (`Promise.all`) صدا می‌زند و هر گزینه‌ای را که تخطی ایجاد کند خاکستری می‌کند -- با پیام دقیق سرور به‌صورت tooltip. هیچ منطق سازگاری‌ای در سمت کلاینت تکرار نشده است. بازگشت و تغییر یک انتخاب قبلی، انتخاب‌های بعدی را دوباره اعتبارسنجی می‌کند (و فقط موارد لازم را پاک می‌کند، نه همه را) و این کار دقیقاً به ترتیب ویزارد انجام می‌شود، به‌جای اینکه کاربر را مجبور به شروع از اول کند. این به‌طور معناداری پیچیده‌تر از تمرین‌های معمول «CRUD به‌علاوه‌ی کمی JS» است: لازم بود عمداً با محدودیت «هیچ منطق سازگاری در سمت کلاینت نباشد» کار کنم و در عین حال بازخورد پیش‌بینانه‌ی بلادرنگ در رابط کاربری بدهم.

**CRUD کامل مبتنی بر حساب کاربری با مرزهای مالکیت درست.** ساخت و کاوش build به‌صورت مهمان ممکن است، اما ذخیره، فهرست، مشاهده، ویرایش و حذف build همگی بررسی مالکیت می‌خواهند و برای build کاربر دیگر پاسخ 404 (نه 403) برمی‌گردانند تا وجود آن لو نرود -- مطابق طراحی API آگاه به امنیت.

## ساختار پروژه

- `config/` -- تنظیمات پروژه و پیکربندی URL اصلی
- `components/` -- مدل‌های 8 دسته‌ی سخت‌افزار (GPU، CPU، Motherboard، CPUCooler، RAM، Storage، PSU، Case) به‌علاوه‌ی `GPUBenchmark`، داده‌ی fixture و ادمین Django
- `compatibility/` -- 9 تابع خالص قاعده‌ی سازگاری، dispatcher مبتنی بر دسته، جدول جست‌وجوی bottleneck که به‌صورت تجربی تست شده، و endpoint با خروجی JSON در مسیر `/builder/check/`
- `builds/` -- مدل `Build`، view ویزارد، view‌های ذخیره، فهرست، جزئیات، ویرایش و حذف، و templateهای آن‌ها
- `users/` -- مدل سفارشی `User` (بدون فیلد اضافه، از روز اول تعریف شده تا راه برای فیلدهای آینده بدون migration مخرب باز بماند) و ثبت‌نام
- `templates/` -- چیدمان مشترک (`base.html`)، templateهای هر اپ، و `404.html` سفارشی
- `static/css/` و `static/js/` -- CSS دست‌نویس (الهام‌گرفته از Material Dark با تأکید آبی) و JS خالص ویزارد (`builder.js`)
- `build_fixtures.py` -- اسکریپت یک‌باره‌ی تبدیل داده که فایل‌های JSON خام و مستقل‌جمع‌آوری‌شده در `components-data/` را به یک fixture استاندارد Django تبدیل می‌کند

## اجرا در محیط محلی

نیازمند Python 3.14، PostgreSQL 18 و هیچ سرویس دیگری نیست.

**۱. نصب وابستگی‌ها**

```
python -m venv venv
venv\Scripts\Activate.ps1        # Windows PowerShell (macOS/Linux: source venv/bin/activate)
pip install -r requirements.txt
```

**۲. ساخت دیتابیس** (در `psql` و با کاربر `postgres`)

```sql
CREATE ROLE rigcraft WITH LOGIN PASSWORD 'choose-a-password' CREATEDB;
CREATE DATABASE rigcraft OWNER rigcraft;
```

دسترسی `CREATEDB` به Django اجازه می‌دهد هنگام اجرای تست‌ها یک دیتابیس موقت بسازد.

**۳. پیکربندی محیط**

فایل `.env.example` را به `.env` کپی کنید (در ویندوز `Copy-Item .env.example .env` و در بقیه‌ی سیستم‌ها `cp .env.example .env`) و این دو مقدار را تنظیم کنید:

- `SECRET_KEY`: با این دستور بسازید: `python -c "import secrets; print(secrets.token_urlsafe(50))"`
- `DATABASE_URL`: `postgres://rigcraft:choose-a-password@localhost:5432/rigcraft`

**۴. بارگذاری داده و اجرا**

```
python manage.py migrate
python manage.py loaddata components/fixtures/components_data.json
python manage.py loaddata compatibility/fixtures/bottleneck_exceptions.json
python manage.py createsuperuser
python manage.py runserver
```

بعد آدرس http://127.0.0.1:8000/ را باز کنید.

**۵. اجرای تست‌ها**

```
python manage.py test
```

## تصمیم‌های طراحی که دانستنشان ارزش دارد

- **موتور bottleneck یک جدول جست‌وجوی تجربی تست‌شده است، نه یک فرمول مبتنی بر نسبت بنچمارک -- و این طراحی اولیه نبود.** نسخه‌ی اول، امتیاز بنچمارک هر CPU و هر GPU را به‌صورت درصدی از قوی‌ترین قطعه‌ی همان دسته مقایسه می‌کرد و بعد اختلاف این دو درصد را با یک ضریب وابسته به رزولوشن وزن می‌داد. خروجی این فرمول زیر بررسی دقیق دوام نیاورد: فرض می‌کند امتیاز بنچمارک تک‌هسته‌ای یک CPU نماینده‌ی قابل‌اعتمادی از عملکرد واقعی آن در بازی است، و آزمون نشان داد این فرض در میکرومعماری‌های مختلف CPU می‌شکند. در حین بررسی دو نمونه‌ی مشخص و مستقل‌مستندشده پیدا شد: نسل Arrow Lake اینتل (Core Ultra 200S) به‌طور عمومی شناخته شده که در بازی‌ها نسبت به نسل قبل ضعیف‌تر از امتیازهای بنچمارک خودش عمل می‌کند، و تراشه‌های دو-CCD سری Ryzen 9 شرکت AMD (مدل‌های 9900X و 9950X) به‌دلیل تأخیر بین‌CCD و رفتار core-parking مستندشده در پلتفرم‌های اولیه‌ی Zen 5 می‌توانند امتیازهای ناهمگون نسبت به یکدیگر و نسبت به همتاهای تک-CCD ضعیف‌تر بگیرند. هیچ‌کدام از این دو الگو را نمی‌شود با فرمولی که فقط بر صدک‌های بنچمارک بنا شده بیان کرد. بنابراین فرمول کنار گذاشته شد و به‌جایش ترکیب‌های واقعی مستقیماً تست شدند: برای هر خانواده‌ی میکرومعماری CPU، ضعیف‌ترین CPU کاتالوگ اول با هر GPU در هر رزولوشن تست شد؛ اگر آن ضعیف‌ترین CPU bottleneck نشان نداد، فرض شد CPUهای قوی‌تر همان خانواده دست‌کم همان‌قدر خوب عمل می‌کنند و جداگانه تست نشدند، چون یک قطعه‌ی قوی‌تر در همان معماری نباید جایی bottleneck باشد که قطعه‌ی ضعیف‌تر نبوده است. هر موردی که bottleneck نشان داد، و هر خانواده‌ی معماری متفاوت، مستقیماً تست شد. نتیجه‌ی مشاهده‌شده‌ی واقعی هر مورد تست‌شده مستقیماً ثبت شد (مدل `BottleneckException`، پر شده از یک fixture ساخته‌شده و دست‌تایپ‌شده). هر ترکیبی که ردیف مطابق نداشته باشد -- چه تست‌شده و موفق، چه استنباط‌شده از موفقیت یک CPU ضعیف‌تر هم‌خانواده -- پیش‌فرضش Balanced است. Cyberpunk 2077 به‌عنوان تنها بازی مرجع این تست انتخاب شد، چون یک عنوان AAA سنگین و گرافیکی است که برخلاف برخی بازی‌های دیگری که در بررسی اولیه نمونه‌برداری شدند، به‌شدت به سمت CPU-bound یا GPU-bound نمی‌رود و نتایج را نسبتاً نماینده نگه می‌دارد، نه بهترین یا بدترین حالت. آستانه‌های `Balanced` / `Minor` / `Major` (استفاده‌ی 94% / 84% از GPU در تنظیمات ثابت) آستانه‌های خود این پروژه‌اند و از هیچ طرح طبقه‌بندی شخص ثالثی گرفته نشده‌اند. **این جدول یک مرجع مفید است، نه یک تضمین دقیق:** فقط یک بازی در یک پروفایل تنظیمات (کیفیت Ultra، بدون upscaling، بدون ray tracing) را بازتاب می‌دهد و شدت واقعی bottleneck با بازی، پریست کیفیت یا تنظیم upscaling دیگری می‌تواند به‌طور معناداری تغییر کند.
- **کاتالوگ GPU عمداً به سری RTX 50 و RX 9000 محدود شده است** (در مجموع 9 کارت)، نه یک کاتالوگ تاریخی جامع، تا مجموعه‌داده یک نمونه‌ی عمداً گزینش‌شده و قابل‌راستی‌آزمایی بماند، نه گسترده و سخت‌تر برای راستی‌آزمایی.
- **زیرمجموعه‌ی DDR4 (2 مادربرد، 2 کیت RAM) عمداً کوچک است.** صرفاً برای نشان‌دادن قاعده‌ی سازگاری نسل DDR بین RAM، CPU و مادربرد وجود دارد، نه به‌عنوان پشتیبانی عمومی از سخت‌افزار قدیمی.
- **بدون قیمت و لینک فروشگاه.** کاملاً از دامنه حذف شده -- این پروژه به «آیا این قطعات با هم کار می‌کنند؟» پاسخ می‌دهد، نه «برای چه قیمتی بخرمشان؟».

## عمداً خارج از دامنه

- **تست جدول bottleneck با بیش از یک بازی مرجع.** جدول جست‌وجو نتایج مشاهده‌شده در یک عنوان (Cyberpunk 2077) با تنظیمات ثابت را بازتاب می‌دهد. تست واقعی در طول توسعه نشان داد که میزان استفاده از GPU برای سخت‌افزار یکسان می‌تواند بسته به اینکه بازی چقدر CPU-محور یا GPU-محور است، بیش از 60 واحد درصد بین بازی‌ها نوسان کند -- بنابراین این نتایج یک نقطه‌ی مرجع معقول برای یک بازی هستند، نه میانگین چندبازی یا تضمینی برای هر عنوان.

## منابع داده

کاتالوگ قطعات یک نمونه‌ی کوچک است که به‌صورت دستی از صفحات عمومی در دسترس و برگه‌های مشخصات (spec sheet) و برای مقاصد آموزشی و نمونه‌کار جمع‌آوری شده است:

- **امتیازهای تک‌هسته‌ای CPU (12 CPU):** PassMark Software (cpubenchmark.net)
- **سوکت و TDP پردازنده‌ها:** صفحات محصول Intel ARK و AMD
- **مشخصات مادربردها:** صفحات محصول ASUS، MSI و Gigabyte
- **مشخصات GPU (VRAM، TDP، طول):** مشخصات عرضه‌ی NVIDIA و AMD؛ مورد RTX 5090 با TechPowerUp تطبیق داده شده است
- **امتیازهای بنچمارک سه‌بعدی GPU و ارقام FPS هر بازی:** exo.ir (جدول‌های FPS بر پایه‌ی داده‌های TechPowerUp هستند)
- **کولرها، RAM، حافظه‌های ذخیره‌سازی، پاورها و کیس‌ها:** برگه‌های مشخصات سازندگان

مقادیر به‌صورت دستی جمع‌آوری و نمونه‌وار بررسی شده‌اند، نه اینکه به‌طور کامل راستی‌آزمایی شده باشند؛ برخی ارقام (برای مثال TDP کولرها یا فاصله‌ی مجاز GPU در کیس) ممکن است اندکی با مشخصات رسمی مدل دقیق تفاوت داشته باشند.

کد منبع کار خودم است. داده‌های بالا متعلق به منابع مربوط به خود هستند، فقط برای نمایش غیرتجاری گنجانده شده‌اند و مشمول هیچ مجوزی که روی کد اعمال شود نیستند. اگر دارنده‌ی حقوق هستید و می‌خواهید چیزی حذف شود، لطفاً یک issue باز کنید تا بی‌درنگ حذف شود.
